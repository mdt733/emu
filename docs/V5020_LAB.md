> four-arm launch, which did not produce a qualifying walker. It remains
> readable solely for reproducing results with the exact original source

**Start:** `emu campaign5020` (plan only). **Run everything:** `emu campaign5020 --run`.

This is the v5015/v5016 **shared-ancestor, four-way successive-halving lab** adapted for
312 observation inputs, noisy two-lane rolling terrain memory, true collidable
inclines, physical steps, varied obstacle placement, and the unchanged
steady/transition/resilience locomotion controller. It replaces manual
`foundation` → `slope` → `steps` stage commands for the big study.

The last 64-world smoke test at source `3fd608d` completed 4,096 steps and
validated its checkpoint. Its 100% fall rate was an untrained-policy result,
not a foundation capability. That smoke checkpoint is NOT reused here.

## The experiment graph (absolute policy steps)

```text
20M  shared cold start; all 312 inputs, gentle REAL contact slopes,
     vx/vy/yaw transitions, push and posture recovery
 |
 +-> balanced       -> 80M --+
 +-> slope_recovery -> 80M --+ frozen, independent common 20mm step,
 +-> step_focus     -> 80M --+ real contact slopes and command/recovery
 +-> efficient      -> 80M --+ examination and results.md
                               |
                   top TWO eligible policies
                               |
                   120M A             120M B
                               \       /
                         held-out physical exam
                                 |
                        best ELIGIBLE policy
                                 |
                             160M final
```

Total nominal environment steps across all forks: **380 million**
(20M + four 60M continuations + two 40M continuations + one 40M final).
Sequential runs share one GPU rather than accidentally running four trainers
on an 8GB card. Step targets are absolute per policy, NOT additional steps.

All four branches retain actual contact slopes, variable 3–30mm MJX
boxes, obstacle/flat rehearsal, sensor noise, all 312 observations,
locomotion scoring, energy accounting, genuine multi-command practice and
resilience. Different arms change ONLY:
- `balanced`: reference course, no extra cost/reward coaching.
- `slope_recovery`: wider contact slope distribution, mild efficiency coaching.
- `step_focus`: additional physical obstacle exposure, tiny supported forward coaching.
- `efficient`: stronger servo-effort coaching on the same nominal physical course.

At 120M the physical step ceiling expands to 50mm, slope/noise intensity
increases. The 160M finalist sees a 60mm ceiling (not a guaranteed achieved
height) and more varied hardware/slopes. The terrain frontier still expands
only on physically demonstrated step evidence.

## Start one entire campaign from WSL

```bash
cd ~/emu-v5020
git pull --ff-only
source .venv/bin/activate
git status --short                   # MUST be empty
emu campaign5020                     # plan: no training, no file writes

# One foreground command; auto-continues through final if eligible.
XLA_PYTHON_CLIENT_PREALLOCATE=false emu campaign5020 --run \
  --envs 512 --screen-envs 32 --seed 733 \
  --root ~/robot_lab/emu_runs/v5020_lab
```

Use `--stop-after round1` if you want 4×80M results and a scorecard
before proceeding; running the SAME command again without `--stop-after`
continues from validated checkpoints/locked selections. Use
`--stop-after foundation` to finish the 20M parent first. The selected
`--envs`, `--seed` and **Git commit must stay unchanged** throughout.

If 512 worlds are too heavy for an 8GB card, choose `--envs 256`
**before starting a fresh root**; never lower envs halfway through a
checkpoint lineage because it changes the update boundary and training
contract. On this GPU, XLA memory preallocation is disabled by default
by the campaign process; other GPU workloads may still cause OOM.

## Competition and safety

Every candidate is frozen and tested against the SAME held-out seeds
and command/recovery profiles, with TWO true contact-slope intensities
and a real 20mm box atop the locally sloped floor. A separate,
JIT-compiled course metric observes real box-foot contact and later upright,
supported passage in the original episode, even without episode timeout.
Being near the box or obtaining training reward earns no crossing. Each contender is evaluated separately at
the same fixed settings and horizon.

Only candidates with valid, finite scores, minimum core/resilience/
contact-slope survival, a real sampled step-course episode and
acceptable chassis height are eligible. Promotions are ordered by
an explicit score including step crossing, core walking, resilience,
slopes and command tracking. If fewer than two (or one) are eligible,
**the autopilot stops** and saves all evidence, rather than inventing
a winner or relaxing the rules. A 20mm exam is an early indicator; it
cannot prove higher 50–60mm crossings or real-world hardware readiness.

Each run retains `metrics.csv`, `fixed_eval.csv`,
`console.log`, `training_config.json`, `lab_spec.json`,
`run_meta.json` and exact final/partial checkpoints.
The root automatically receives `results.md`,
`results_data.json`, `results_bundle.zip`, and per-round
`roundN_scoreboard.json` / `roundN_scorecard.md`.
All raw GPU results live OUTSIDE Git and the public showcase remains unchanged.

Safeguards: one foreground campaign lock, source-commit pin,
full observation/sensor-contract validation, checkpoint hash checks,
parent lineage locking, clean Git, automatic restart of incomplete runs,
reuse of current frozen scoreboards, fail-closed eligibility.

You can inspect progress without restarting:

```bash
emu campaign5020 --status
tail -n 50 ~/robot_lab/emu_runs/v5020_lab/foundation20/console.log
cat ~/robot_lab/emu_runs/v5020_lab/results.md
```

Historical `emu ladder` remains for now because the single-run `emu train`
CLI shares its implementation. The v5016 Pinnacle campaign executable was
retired from this research branch; its original implementation is preserved
untouched on `main`.

**Warning:** source pinning is intentional. After a training
checkpoint has been created, keep its source revision pinned. Changes to
this same feature branch require a **different fresh output root** unless
resuming with the exact original commit; do not create more Git branches
solely to preserve old experiments. No permanent publication or merge to `main`
is performed by this campaign.
